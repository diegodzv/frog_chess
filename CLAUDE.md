# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Qué es esto

Torneo de ajedrez de una oficina (20-200 personas), jugado en chess.com. Formato "estilo Pokémon VGC": 6 rondas suizas semanales (se comunican el lunes a las 9:00 y se juegan hasta el domingo 23:59, del 9 de noviembre al 20 de diciembre de 2026) y, tras el parón de Navidad, eliminatoria (single elimination) en enero con los mejores clasificados. Cada emparejamiento es una **serie**: el suizo es a **una sola partida** (Bo1), semifinales y final al mejor de 3 (Bo3) y las rondas anteriores del cuadro por decidir según inscritos (de momento Bo3). **Las tablas no cuentan: se juega otra partida (o, en el suizo, los jugadores pueden echarlo a suertes, que el organizador mete a mano); nunca hay encuentros empatados.** "Frog" es la mascota de la empresa del usuario, sin relación funcional. La app importa a los inscritos, genera emparejamientos, detecta resultados en chess.com y publica ranking, rondas, bracket y estadísticas. Normas para los participantes: documento de Claude Docs del usuario («Frog Chess: normas del torneo»), no está en el repo. Documentación, mensajes de error de cara al organizador y mensajes de commit en español; identificadores y comentarios de código en inglés.

## Comandos

Dos paquetes npm independientes, sin lint ni formateador configurados. Node 20 (`.nvmrc`; el local es 24 y también vale).

```bash
# Backend / scripts (scripts/)
cd scripts && npm install
npm test                                              # node --test: descubre solo los *.test.mjs (no le pases directorios: falla en Node >=22)
node --test __tests__/series.test.mjs                 # un solo fichero
node --test --test-name-pattern="Bo5" __tests__/series.test.mjs   # un solo test
npm run spike                                         # comprueba el comportamiento de tournament-organizer (sin red)
npm run smoke:chesscom                                # llama a la API real de chess.com (necesita red sin filtro)
node build-public-data.mjs                            # regenera data/public/*.json; puro, sin red ni git
node import-players.mjs <export.csv> [--check] [--dry-run]   # inscripciones de Microsoft Forms -> data/players.json; no commitea
npm run reset -- --yes [--keep-players]               # vuelve a fase de inscripción (para pasar de pruebas al torneo real); no commitea

# Simulación (fake players + partidas simuladas; NO toca data/)
node dev/simulate-tournament.mjs                      # (= npm run sim) 20, 40 y 60 jugadores -> sim/n20, sim/n40, sim/n60 (+ 2 snapshots a medias) y estadísticas
node dev/simulate-tournament.mjs --players=200 --seed=7 --runs=20 --no-show=0.05
node dev/simulate-tournament.mjs --swiss-rounds=7 --cutoff=8 --out=/tmp/sim   # probar otro formato sin pisar sim/

# Frontend (web/)
cd web && npm install
npm run dev        # predev copia data/public -> web/public/data y sim/*/public -> web/public/data/sim/* (gitignored)
npm run build      # salida en web/dist
# Ver una simulación: http://localhost:5173/stats.html?data=sim/n40  (hay un selector "Datos:" en la barra si existe sim/)
```

El simulador lee `data/tournament.json` (formato real); los tests llevan su propia configuración. Los tests de motor, flujo, simulación, datos públicos, reset, roster y sync usan el paquete real `tournament-organizer` (no mockeado). `roster.test` (`import-players.mjs`) y `syncResults.test` (`sync-results.mjs`) ejecutan el script como proceso con chess.com simulado por `__tests__/helpers/stub-chesscom*.mjs` (cargados con `--import`). Ningún test usa red real. Pasan los 97 tests (sin `npm install` previo, los que importan el motor fallan con `ERR_MODULE_NOT_FOUND: tournament-organizer`).

Guía de uso para el organizador (Forms, importación, rondas, overrides, cambios de rival): `docs/ORGANIZADOR.md`.

## Gotchas

- **Los scripts que escriben datos hacen `git add data && git commit && git push` de verdad** (`sync-results`, `advance-tournament` vía `lib/commitAndPush.mjs`; `import-players` y `reset` no commitean). Para ejecutarlos en local sin efectos: `FROG_SKIP_GIT=1` (no commitea) y `FROG_DATA_DIR=<dir>` (lee y escribe otra copia de `data/`; `lib/repoData.mjs`). El simulador y las pruebas de E/S usan ambos.
- **La ventana de una ronda abierta llega hasta "ahora"** (`endedAt: null` -> `Date.now()`): un test con partidas fechadas en el futuro no encuentra nada. `syncResults.test` fecha todo relativo a `Date.now()`.
- **Los exportes de Forms contienen correos**: `*.csv` y `*.xlsx` están en `.gitignore`; el correo solo sirve para quedarse con la última respuesta de cada persona y nunca se escribe en `data/`.
- **Los `package-lock.json` de `scripts/` y `web/` deben estar commiteados**: todos los workflows hacen `npm ci` con `cache-dependency-path: */package-lock.json` y fallan sin ellos.
- **Redespliegue tras los commits del bot**: los push hechos con el `GITHUB_TOKEN` no disparan `deploy-pages.yml`, así que `sync-results` y `advance-round` terminan con un paso que ejecuta `gh workflow run deploy-pages.yml` solo si su `HEAD` cambió (necesitan `permissions: actions: write`). **Escrito pero sin probar en GitHub**.
- **Formato de PGN de chess.com, verificado el 2026-10-27** con ~1000 partidas reales (blitz 3+0/5+0 y 3+1): un `{[%clk h:mm:ss.s]}` por jugada, con el incremento ya sumado (el reloj sube tras jugar rápido); etiquetas `UTCDate`/`UTCTime`/`StartTime`/`EndDate`/`EndTime` en UTC; el recuento de jugadas de `countPlies` coincide en todas con el número de jugada del FEN final. La duración por relojes (tiempo de juego) sale ~16 s (mediana) menor que la de reloj de pared por las etiquetas. El archivo mensual trae además `accuracies` (solo si alguien analizó la partida), `tcn`, `uuid`, `initial_setup`, `eco` y `rating` de cada lado.
- El repo tiene `core.autocrlf=true`: los ficheros originales están en CRLF y los añadidos después en LF. No lo "arregles" en masa; si editas con scripts, tenlo en cuenta al hacer reemplazos de texto.
- El repo es `github.com/diegodzv/frog_chess` (Pages en `diegodzv.github.io/frog_chess/`); `REPO_URL` y el `USER_AGENT` de chess.com ya lo usan. `battle_subway_helper/` (otro proyecto del usuario copiado dentro del directorio, con su propio repo/Pages) está en `.gitignore`: no mezclarlo.
- Cortafuegos de la oficina bloquea chess.com: `smoke:chesscom`, `import-players --check` y cualquier prueba con red real hay que hacerlas desde otra red. Los runners de Actions no se ven afectados (por eso existe la acción `check-players`).

## Decisiones de diseño (no renegociar sin motivo)

- **Cero backend propio y cero servicios de pago**: GitHub Pages sirve estáticos, JSON versionado en `data/` es la "base de datos", GitHub Actions es el "backend". Repo público (Pages gratis en cuenta personal no admite privados): nombres reales y usernames quedan visibles. Netlify + Firebase se valoró y se descartó (reescribir la capa de datos a días del inicio; las Functions de Firebase exigen plan de pago).
- **chess.com PubAPI** (`api.chess.com/pub`): solo lectura, sin auth. Sí manda `Access-Control-Allow-Origin: *` (comprobado), pero por diseño solo se llama desde Node (workflows/scripts) y la web lee JSON ya calculado. No hay forma oficial de verificar que alguien es dueño de un username; cada jugador lo declara.
- **Node.js, no Python** (confirmado explícitamente por el usuario), para reutilizar `tournament-organizer` (swiss con blossom matching + tiebreaks), sin equivalente maduro en Python.
- **Registro con Microsoft Forms** (decisión del usuario: nadie tiene que crearse cuenta de GitHub; la oficina usa Teams). El organizador exporta el Excel como CSV y `import-players.mjs` (`lib/roster.mjs`) lo fusiona en `players.json`: columnas por título de pregunta ("Nombre y apellidos", "Usuario de chess.com"), delimitador `;`/`,` detectado, última respuesta por correo, usernames duplicados descartados, enlaces de perfil y `@` aceptados, idempotente. Los importados quedan `chesscomVerified: false` y **`start-tournament` se niega hasta que la acción `check-players`** (o `--check` en local) los valide contra chess.com y normalice mayúsculas.
- **Avance de ronda MANUAL** (`workflow_dispatch` de `advance-round.yml`: `check-players | start-tournament | apply-overrides | rebuild-public-data | next-round | force-next-round`). Nunca automático por fecha: el organizador pulsa cada lunes antes de las 9:00 (a los jugadores se les comunica a las 9:00), y ese momento abre/cierra la ventana de la ronda.
- **Resultados nunca adivinados**: partidas inconsistentes o jugadas con otro ritmo/variante/sin puntuar -> `needs-review.json`; serie sin decidir -> pendiente. Una partida no jugada jamás se forfeitea sola: requiere entrada manual en `overrides.json` + `force-next-round`.
- **Formato (en `data/tournament.json`)**:
  - `swissRounds: 6` (decisión del usuario; `"auto"` = `ceil(log2 n)` sigue existiendo). Corte a eliminatorias `"value": "auto"` = mayor potencia de 2 <= n/2 acotada a [4,32] (20->8, 40->16, 60->16, 100+->32); el número final lo decidirá el usuario según inscritos. Un número explícito manda sobre `auto`; el corte tiene que ser potencia de 2. Se resuelven al iniciar el torneo y se guardan como números.
  - Series (`"series"`): `swiss: 1`, `elimination: 3`, `semifinal: 3`, `final: 3` (decisión del usuario; `elimination` por decidir). `DEFAULT_SERIES` de `lib/series.mjs` sigue con Bo5 en semis/final: solo lo usan los tests sin `series`. Sin partido por el 3.er puesto. `timeClass: "blitz"` porque el ritmo previsto (6+2) es blitz en chess.com; el ritmo definitivo está por decidir y el usuario avisará (no tocarlo antes).
  - Reglas de serie (`lib/series.mjs`, definidas por el usuario): la serie termina cuando alguien llega a `ceil(bestOf/2)` victorias; una partida en tablas no puntúa y se repite, por lo que un "Bo3" puede durar más de 3 partidas. No existen encuentros empatados: `applySeriesResult` rechaza cualquier marcador que no sea `need`-N con N < need.
  - Puntos: serie ganada 1, perdida 0, bye 1 (sin medios puntos). **Resistencia** (pedida explícitamente por el usuario como valor de cada jugador, visible en todas las clasificaciones, no solo como desempate; ordena tras los puntos): `opponent match win percentage` (win % medio de TODOS los rivales, con su récord final) y luego `opponent opponent match win percentage`. Lo calcula la librería: sin el mínimo del 25 % de Pokémon y contando los byes en el win % de los rivales. Antes era Buchholz mediano, que descarta al mejor y al peor rival (justo el caso "perdí contra el 6-0" que el usuario quiere premiar); en simulación ningún desempate cambia de forma medible quién gana.
  - Comparado con Play! Pokémon (Tournament Rules Handbook §5.5.1, §5.6.1, §5.5.4.1): el bye de la librería es el suyo —ronda 1 al azar; después al peor récord sin bye previo, nunca dos veces— y `verifyTournament` lo comprueba como invariante. Con puntos enteros el corte lo decide casi siempre el desempate (10-16 empatados en la línea con 40-60 jugadores); es inherente a suizo + corte.
- **Sin cambio de rival**: la regla de reemparejar a quien no consigue contactar con su rival se descartó; quien no juega pierde la partida (override `winner`/`loser`). El `swapOpponents` que la implementaba se eliminó (está en el commit 3d0ddf9 si hiciera falta).
- **Estadísticas** (pedidas por el usuario): victoria más rápida en jugadas y en tiempo, quién gana más rápido de media (desde 2 victorias), victoria con más material y más jaques mate. **Solo nombran al ganador** (no señalar al que pierde). Excluyen partidas abandonadas, de menos de 5 jugadas y resultados manuales.

## Arquitectura

```
Microsoft Forms ─▶ (CSV) import-players.mjs ─▶ data/players.json ─▶ check-players (Actions, chess.com)
organizador ─▶ advance-round.yml ─────▶ data/engine-state.json + data/tournament.json   (lib/tournamentFlow.mjs)
cron horario ▶ sync-results.yml ──────▶ series desde chess.com + detalles de partida (meta.chesscomGames)
                         └─ todos terminan en build-public-data.mjs ─▶ data/public/*.json (incl. stats.json)
push a main (data/public/** o web/**) ─▶ deploy-pages.yml ─▶ web/ (Vite+React) en GitHub Pages
push a main / PR ─▶ ci.yml ─▶ npm ci + npm test (scripts/) y npm ci + npm run build (web/)
```

Los workflows que escriben en `data/` comparten `concurrency: {group: tournament-data, cancel-in-progress: false}`: se encolan.

Cosas que exigen leer varios ficheros para entenderlas:

- **`lib/tournamentEngine.mjs` es el único punto de contacto con `tournament-organizer`** (v4.1.1 fijada). Su cabecera documenta lo verificado leyendo el código de la librería y con `npm run spike`: `Manager` es el export *default*; `nextRound()` solo existe en stage one y tras la última ronda suiza construye TODO el bracket de golpe (rondas numeradas a continuación de las suizas); en stage two los cruces avanzan solos con `enterResult()`, `tournament.round` no se mueve y el estado nunca pasa a `complete` salvo que se llame a `endTournament()`; `scoring.bestOf` es global y mutable y `enterResult` valida contra él (máx. victorias = `round(bestOf/2)`), así que `applySeriesResult` lo fija por partido antes de registrar; `assignLoss()` no sirve para el doble forfeit (lanza al segunda llamada), por eso `applyDoubleForfeit` escribe la derrota directamente; el emparejamiento suizo de la librería evita rivales repetidos leyendo `player.matches[].opponent`; el `Swiss` de `tournament-pairings` baraja con `Math.random` en cada ronda (los sorteos no son reproducibles; el simulador siembra `Math.random`). Cada script rehidrata desde `data/engine-state.json` y guarda con `saveEngineTournament` (claves ordenadas -> diffs estables). `engine-state.json` no se edita a mano (es `null` hasta `start-tournament`).
- **`lib/tournamentFlow.mjs`** (`startTournament`, `advance`, `applyPendingOverrides`) es el ciclo de vida como transiciones puras, sin E/S: lo usan `advance-tournament.mjs` y el simulador (la misma ruta que producción). `advance` no muta lo que recibe y lanza sin dejar nada a medias.
- **Dos estados en paralelo**: la librería lleva emparejamientos y puntos; `data/tournament.json` lleva lo que no modela — `phase` (registration -> stage-one -> stage-two -> complete), `currentRound` y `rounds[]` (`number, phase, label, bestOf, startedAt, endedAt`). En stage two `currentRound` es nuestro: la librería activa un cruce en cuanto acaban sus dos feeders, pero la ronda solo "se abre" (y solo se sincroniza) cuando el organizador avanza; por eso `getUnresolvedMatches(engine, round)` filtra por ronda y la web muestra esos cruces como "Por jugar", no "Pendiente". Tras la final, `advance` llama a `finishTournament`.
- **Detección de resultados** (`resultMatcher.findSeriesForPairing` + `sync-results.mjs`): consulta los archivos mensuales de chess.com del jugador A (= player1 del partido), se queda con las partidas entre los dos dentro de la ventana de la ronda, aparta (y reporta como `wrong_format`) las de otro `timeClass`/`rules`/no puntuadas si `requireRated`, las ordena por `endTime` y las puntúa con `scoreSeries` (tablas no cuentan; partidas tras la decisión se ignoran). `complete` -> `applySeriesResult` con la secuencia en `meta.games` y los detalles (`describeGame`: jugadas, duración, material, terminación) en `meta.chesscomGames`; `in_progress` -> solo actualiza `meta.games` (la web enseña el ½ de un Bo1 en tablas, pendiente de otra partida o de un sorteo por override). `sync-results` sobrescribe `needs-review.json` entero en cada ejecución.
- **Identidad de jugador**: `players.json[].id` (`slugify(nombre, usuario)`) es el id del jugador en el motor y `chesscomUsername` se copia a su `meta` dentro de `engine-state.json` (de ahí lo leen `sync-results` y los overrides por usuario). Un jugador importado después de `start-tournament` no entra en el motor. El desempate final de la librería hace `parseInt(id, 36)`: con ids `p_nombre-hash` es constante (orden de inscripción), inocuo pero no significativo.
- **Overrides** (`data/overrides.json`, entradas manuales del organizador): por `matchId` + `outcome`, o por usuarios de chess.com: `{"winner","loser"}` (serie ganada 1-0 en Bo1 / 2-0 en Bo3 / 3-0 en Bo5: sorteos tras tablas y walkovers), o `{"players":[a,b],"outcome":"double_forfeit"}` (solo suizo). Se aplican en orden, solo a partidas sin resolver de la ronda actual y solo una vez (`applied: true`); las que no coinciden con nada se devuelven en `skipped` y el workflow avisa; un resultado imposible lanza. Acciones: `apply-overrides` (aplica sin avanzar), `force-next-round` (aplica y avanza; aborta listando las pendientes sin cambiar nada) y `next-round` (avanza solo si no queda ninguna). `rebuild-public-data` regenera `data/public/` tras editar `players.json` a mano.
- **`build-public-data.mjs`**: `derivePublicData` es pura (`{tournament, roster, engineState, now}` -> `meta, standings, rounds, bracket, players, stats`; `standings.final` es la clasificación general de `engine.getStandings()` una vez existe el cuadro: vivos, eliminados por ronda y el resto, cada grupo por puntos y resistencia de TODO el torneo); `buildPublicData` solo hace E/S y conserva el `updatedAt` anterior si el contenido no cambió (si no, el cron horario generaría un commit y un redeploy cada hora). Los puntos y la resistencia salen de `getSwissStandings` de la librería (`tiebreaks.oppMatchWinPct`/`oppOppMatchWinPct`), no se recalculan; las victorias por serie/partida se cuentan a partir de los `matches`. `stats.json` sale de `lib/gameStats.mjs` (`winsFromMatches` sobre `meta.chesscomGames` + `buildStats`). Ojo: `player.value` de la librería es la siembra (siempre 0 aquí), no los puntos.
- **Frontend** (Vite multi-página: `index/round/bracket/stats.html`, `base: './'`): pide los JSON en runtime con `useJson` (`cache: 'no-store'`); `src/dataset.js` resuelve `?data=sim/<n>` para ver simulaciones. `round.html` navega todas las rondas (`?round=N`; es la página que se comparte cada lunes), `bracket.html` pinta cada ronda con su Bo y marcadores. La pestaña «Normas» enlaza al documento de normas (`RULES_URL` en `web/src/config.js`; vacío = pestaña oculta); no hay página de inscripción. **Sin textos explicativos en la UI** (decisión del usuario: nada de banners, leyendas sobre formato/desempates/siembra ni contadores; eso va en las normas). No se muestran la siembra ni la secuencia V/D/½ de partidas (no hay local ni visitante). `web/public/data/` es una copia derivada (`web/copy-data.mjs`); `sim/` está en `.gitignore`, así que las simulaciones nunca llegan al despliegue.
- **Simulación** (`lib/simulation.mjs`): jugadores con Elo oculto, partidas con expectativa Elo y tablas más raras cuanto mayor la diferencia, no-shows (overrides vía `force`), `stopAt` para snapshots a mitad de ronda, y detalles de partida inventados (con su propio RNG, para no alterar los sorteos de cada semilla) para que la página de estadísticas tenga datos. `verifyTournament` comprueba invariantes (todos juegan una vez por ronda, sin repetir rival, byes, siembra 1 vs N, Bo correctos, un campeón) y calcula métricas del formato; sus propios tests lo manipulan para comprobar que falla cuando debe. Con 200 jugadores y 6 rondas, 20 torneos simulados tardan ~10 s y salen sin incidencias.
